# rust-kvm

把 USB 采集卡和 CH9329 键鼠控制器做成局域网服务，用浏览器远程控制被控电脑。

前身是 [chrome-kvm](../chrome-kvm)：那一版整套跑在浏览器里，画面走 `getUserMedia`、
键鼠走 Web Serial，所以网页必须开在插着硬件的那台机器上。这一版把设备独占和网络
出口交给一个 Rust 服务，网页只管界面和协议，于是任何一台能开浏览器的设备都能连进来。

## 跑起来

```bash
cargo run
```

Linux 上先装这几个（cpal 要 ALSA 的头文件，serialport 靠 libudev 枚举 USB 串口，
openh264 的 SIMD 汇编要 nasm）：

```bash
sudo apt install pkg-config libasound2-dev libudev-dev nasm
```

**nasm 别漏。** 没有它 openh264 照样编得过、只在构建输出里悄悄说一句不用汇编，
编码慢一倍多（1080p 一帧 23 ms 对 9 ms），H.264 就上不了 60fps。装上之后要
`cargo clean -p openh264-sys2` 再编，否则沿用的还是之前那份纯 C 的。

启动后日志里会列出所有可访问地址：

- **本机调试**：`http://localhost:8080/` —— 只绑回环，不用跟证书较劲。
  `localhost` 在浏览器里本身算 secure context，功能不缺。
- **局域网访问**：`https://<本机IP>:8443/` —— 必须走 HTTPS。

首次从别的机器访问会撞上自签名证书警告，点「高级 → 继续前往」即可，或者下载
`/cert.crt` 装进受信任的根证书颁发机构，之后就不再提示。

**HTTPS 不是为了安全，是硬性依赖**：Keyboard Lock（转发 Win / Alt+Tab 这些系统键）、
剪贴板读取（粘贴文本到被控端）、Pointer Lock（相对鼠标模式）这三个 API 都只在
secure context 下可用。所以局域网那一侧没有明文选项。

证书按本机所有 IPv4 和主机名签发，缓存在 `certs/`。换了网络导致 IP 变化时会自动
重签——否则浏览器会因为 SAN 不匹配直接拒连，而且报错很难看懂。

## 诊断工具

```bash
cargo run --bin probe
```

列出采集设备、打印支持的 MJPEG 格式，然后按 1080p 采集 5 秒，报告实测帧率、
单帧字节数和码率，并检查拿到的字节是不是真的 JPEG。换采集卡或者画面出问题时
先跑这个。

```bash
cargo run --bin probe-audio
```

列出音频输入设备和它们自报的格式，录 5 秒并写出 `audio-probe.wav`，同时报告电平
和一个字节对齐检测。**跑的时候要让被控机出声**，否则全静音下什么都看不出来。

这个检测是为 MS2109 的一个已知毛病准备的：Linux 内核对 `0x534d:0x2109` 打了
`stream_offset_adj = 2`——设备在流开头多吐 2 个字节，使 16 位样本整体错位一个字节，
听起来是震耳的噪声。Windows 的 usbaudio.sys 未必打了同样的补丁。判断办法是拿同一段
字节按两种对齐各解一遍，比相邻样本的相关系数：真实音频接近 1，错位后的垃圾接近 0。
采样率对不对只能靠耳朵，所以顺手写了 WAV——放出来变调就是采样率不符。

## 设计要点

### 视频为什么不转码

本机那张卡是 **MS2109**（USB 2.0 HDMI 采集棒），能力表只有两种选择：MJPEG
1080p 能到 30fps，而 YUY2 原始帧在 1080p 下只有 **5fps**。也就是说 MJPEG 是唯一
可用格式，而它已经是压缩过的。

既然卡吐出来的就是一帧帧 JPEG，最低延迟的做法就是**原样转发**：服务端一次都不
解码，浏览器直接拿去显示。这比转成 H.264 少了一次解码加一次编码，延迟只低不高，
代价是码率从 6 Mbps 左右涨到 20–40 Mbps——局域网无所谓。

实测（静态桌面画面）：30 fps，单帧约 90 KB，21 Mbps，浏览器端解码约 6 ms。
画面内容越动态码率越高，所以配置里需要能降分辨率或帧率。

上面这套的前提是「带宽不要钱」，出了局域网就不成立了——所以有了下面那个可切换的
低带宽模式。默认仍然是 MJPEG：转码这件事，只在带宽真的是瓶颈时才划算。

### 低带宽模式：H.264，静止画面几乎不要钱

20–40 Mbps 走 VPN 出门是不可能的。开了 `codec: "h264"` 之后服务端多挂一条链路：
MJPEG 解码（`zune-jpeg`）→ NV12（`nv12.rs`）→ 硬件编码器（Media Foundation 的
`AMDh264Encoder`，封在 `h264.rs`）→ 还是那条 `/ws/video`，客户端用 WebCodecs 的
`VideoDecoder` 解。不引 ffmpeg，不引 WebRTC。

**关键的不是压缩率，是「不动的时候不要钱」。** KVM 的画面大部分时间是静止的，而
MJPEG 不管画面动不动都按帧收费。所以码率控制用的是**恒定质量 + 硬上限**而不是 CBR：
最初写的是 CBR，实测发现它会把码率填满——对着完全静止的桌面照样跑 3.93 Mbps。
换成 `eAVEncCommonRateControlMode_Quality` 加 `MaxBitRate` 之后，静止桌面
**0.02 Mbps**，动起来才涨，且有天花板。

| | MJPEG | H.264 |
| --- | --- | --- |
| 完全静止 | 约 0（重复帧不发，见下节） | 0.02 Mbps |
| 只有光标闪／时钟跳 | 每变一次一整帧 63 KB | 几百字节 |
| 整屏在动 | 15–45 Mbps | 封顶（默认 4 Mbps） |
| 到帧→绘制 | 约 8 ms（含解码） | 0.8–1.0 ms |
| 宿主机开销 | 无 | 解码加编码约 8 ms/帧 |

中间那一行才是分水岭。**「完全静止」两边都便宜，但真实桌面几乎从不完全静止**——
有个跳秒的时钟、闪烁的光标，MJPEG 就得把整整 63 KB 再发一遍，而 H.264 只描述变了的
那一小块。所以去重解决不了 H.264 解决的问题，反过来也一样。

两条路的取舍是清楚的：局域网用 MJPEG（延迟最低、宿主机零开销），出门用 H.264。
开关在设置页，**切换不用刷新控制页也不会断连**——`/ws/video` 的第一条 Text 报的就是
这条连接实际在发什么编码，格式变了就重发一条。

还有个同一个道理的小开关：裸 PCM 立体声 48k 是 1.5 Mbps，在 5 Mbps 的预算里和画面
差不多贵。「窄带音频」降混成单声道 24 kHz，四分之一，384 kbps。降采样前有个
`[1,3,3,1]/8` 的低通——直接抽取会让 12 kHz 以上的内容折回可听频段，那种失真听起来
是发毛发沙，很难指着说出哪里不对。

细节、踩过的坑和为什么不用 WebRTC，都在
`docs/superpowers/specs/2026-09-13-h264-low-bandwidth-design.md`。

### 重复帧不发（MJPEG）

**画面静止时，采集卡吐的是逐字节相同的 JPEG。** 实测 6 秒 181 帧只有一个哈希、一个
大小（63163 字节）。既然客户端画布上已经是那一帧了，再发一遍就是纯浪费——不发是
**无损**的，画面一模一样。实测静止时 8 秒只发 1 帧，0.063 Mbps 对原来的 15.8。

比对放在**每条连接**里（`pump_mjpeg` 各自记住上一帧），不是在 hub 里存一份共用的。
这样新观看者的「上一帧」天然是空的，第一帧自然会发给他；放 hub 里反而要专门处理
「静止时有人进场」，不处理就是黑屏——那正是 H.264 那条路上靠强制 IDR 解决的同一个
问题，没必要再制造一遍。63 KB 的比对一个观看者一秒不到 2 MB，不值得为它设计什么。

有个副作用必须处理：**静止和卡死在线上长得一模一样**，都是什么都不来。所以静止满
两秒会发一条 `{"op":"idle"}`，页面据此显示「画面静止（已省 N 帧重复画面）」而不是让
收帧计数僵在那里。这条通知顺带当心跳，免得 NAT 掐掉没有流量的连接。

这条只对 MJPEG 有意义。H.264 那边静止时本来每帧就只有几十字节，去重省不下什么，
反而会打乱编码器的时间戳节奏。

顺带把统计口径也拆开了。原来服务端只报一个码率，数的是**采集卡吐出来的字节**——
不管画面动不动都是 15.8 Mbps，于是「静止画面也要 15.8 Mbps」这个错误结论会一直挂在
屏幕上。现在分成「采集」和「发送」两个数，后者才是真正写进 WebSocket 的（静止时
0.000，H.264 时 0.02）。这两个数在去重和 H.264 之后差着两三个数量级，混成一个就等于
没报。

### 键鼠为什么不在 Rust 里实现协议

服务端只做两件事：独占打开 COM 口，把字节原样搬进搬出。组帧、校验、ACK 重试、
波特率探测这些全留在浏览器里的 `ch9329.js`，那是从 chrome-kvm **原文件拷过来的，
一个字节都没改**——连 44KB 的协议字节测试都还适用。

能这么省事是因为 `ch9329.js` 从一开始就只依赖抽象的 `writer` / `reader`，不认识
Web Serial 本身。`web/serial-ws.js` 伪造了一个同形状的 `SerialPort` 对象（`open`、
`close`、`readable`、`writable`），底下换成 WebSocket，协议代码察觉不到区别。
`Ch9329.connect` 的波特率探测也照原样跑：它探测的做法本就是反复 close / open，
而桥的 `open` 自带波特率、可重复调用。

代价是控制端必须是浏览器。要做原生客户端时再在服务端实现协议也不迟。

唯一的例外是 ARM 板的「本机 USB 口直连」（见下文）：那里没有芯片，服务端的
`src/hid_emulator.rs` 假装成一块 CH9329，把浏览器发来的帧翻成 HID 报告写进
`/dev/hidg*`，再按芯片的格式回应答，`ch9329.js` 照样不用改。

### 端点分工

同一个端口下按路径分流，互不干扰：

| 端点 | 内容 |
|------|------|
| `/` | 静态页面 |
| `/settings.html` | 设置页 |
| `/api/video/stats` | 采集状态、实测帧率与码率 |
| `/api/audio/stats` | 采音状态、格式与码率 |
| `/api/devices` | 摄像头 / 音频输入 / 串口，每类带各自的失败原因 |
| `/api/config` | `GET` 读、`PUT` 写 `config.json`，写完热切换 |
| `/api/serial/ports` | 宿主机上的串口列表 |
| `/ws/video` | 每条 Binary 消息 = 一帧 JPEG |
| `/ws/audio` | 一条 Text 格式头，随后每条 Binary = 一块 Int16 LE PCM |
| `/ws/serial` | CH9329 协议字节透传 |
| `/cert.crt` | 下载自签名证书 |

### 采集按需启停

采集卡是独占设备，被服务占着别的程序就打不开。所以只在有观看者时才开流，最后
一个人离开 3 秒后关掉。留这 3 秒是因为刷新页面会断开重连，而 MS2109 重新打开要
接近一秒。

设置页勾上「没人看时也保持采集」（配置里的 `video.keepCapturing`）就改成服务一起来
就采、一直不停，打开控制页不用等采集卡。只改这个开关不会重开采集；H.264 编码仍然
只在有人看时才跑。开着它时别的分辨率测不了帧率，因为采集卡一直被占着。

**服务运行期间，原来的 chrome-kvm 页面用不了同一张采集卡**，两者不能同时跑。

### 热插拔恢复：三条路，三种不同的「死法」

拔掉采集卡或 CH9329 之后能自己接回来。三条通路的守护方式不一样，因为它们的
「死」表现得完全不同。

**画面**（实测通过）。采集循环出错就退出，`supervise` 等一秒再来，只要还有观看者
就一直重试。实测把采集卡的视频接口禁用掉，`capturing` 立刻转 false 并写明原因；
恢复后 6 秒内自己接上，8 秒时已是满帧——那几秒是 Windows 重新枚举设备的时间，
不是我们在磨蹭。

**声音**。守护结构和画面一样，但这里有两个坑，都得单独挡：

1. **cpal 的流错误不能一律当瞬时**。`ErrorKind` 里只有 `Xrun`（欠载/溢出）和
   `DeviceChanged`（路由变了、cpal 自己重定向好了，文档明说不用重建）是瞬时的，
   其余——特别是 `DeviceNotAvailable` 和 `StreamInvalidated`——意味着流已经死了。
   之前这里把所有回调错误都只写给人看，于是设备一拔就永久卡在「正在采音、
   0 kbps、没有错误」。现在**只白名单那两个**，未知错误按致命处理：猜错的代价
   差得太远——按致命最坏是白重建一次流（声音断一下就回来），按瞬时则是永久假活，
   而且永远不会自己恢复。
2. **回调可能干脆不再被调用**。WASAPI 上设备被拔掉时 cpal 不一定报错。所以另加
   一道兜底：有人听却三秒一个数据块都没来，就认定停摆、收摊重建。输入流即使源是
   静音也会持续送缓冲，所以这个判据不会误伤正常的流。

**键鼠**。串口掉线后自动重连，3 秒一次。这条以前是**纯空话**——状态栏写着
「插回 CH9329 后会自动重连」，而代码里一行重连都没有。而这个场景恰恰是常态：
设置页写完波特率**必须**把 CH9329 断电重插才生效。实测（用重启服务模拟桥断开）
零点击恢复，中间状态是红色的「串口已断开 / 正在自动重连…」。

两个要点：

- **被接管（`busy`）时绝不自动重连**，那是抢。两个开着的页面都自动抢的话会互相
  抢到没完。要抢必须是人点的。
- **每次重连都重新问一遍串口列表**。拔插之后 Windows 偶尔会重新分配口号，死盯着
  旧名字会永远连不上。

没用硬件验到的两条：**真拔 USB** 时的音频设备移除、以及 CH9329 被拔时那条
「桥还活着、口没了」的路径（`onserviceerror`）。两者走的都是上面已经验过的同一套
恢复机制，只是触发点不同。软件禁用设备模拟不了它们——设备正被占用时
`Disable-PnpDevice` 直接失败，而真拔线不管这个。

### 丢帧是设计而不是故障

KVM 要的是当前画面，补发积压的旧帧只会让显示越来越滞后。所以服务端和浏览器端
都只保留最新帧：

- 服务端 broadcast 通道只缓 4 帧，慢客户端触发 `Lagged` 就跳过
- 浏览器端只留一个待解码槽位，解码跟不上到帧速度时直接覆盖

叠加信息里的「丢帧」计数不为零很正常，只要绘制帧率还在 30 左右就没问题。

### 为什么画面也走 WebSocket

`<img>` 加 multipart HTTP 其实略快一点也更省 CPU，因为浏览器原生图像管线接管，
每帧不唤醒 JS。选 WebSocket 是为了换三样它给不了的东西：拿得到每帧到达时刻（才能
做帧率显示和卡顿检测）、能在同一条连接上请求暂停或改分辨率、以及和音频、串口
共用同一套重连逻辑。

代价是每帧多一次 JS 事件循环跳转。这部分放进 Worker 用 `createImageBitmap` +
`OffscreenCanvas` 解码绘制，主线程完全腾出来给键鼠事件，免得解码抖动拖累输入响应。

### 串口读写为什么挤在一个线程里

Windows 上 `serialport` 打开的是同步句柄，一个阻塞在 `ReadFile` 里的读会把同一
句柄上的写一起挡住，`try_clone` 复制出来的句柄指向同一个文件对象，也躲不开。所以
不用「读线程 + 写线程」，改成一个线程每毫秒轮询：先看有没有要写的，再用
`bytes_to_read()` 问有没有数据可读，有才真去读。

同一个线程还负责保证**出串口的包间隔不小于 4ms**。芯片按「空闲超过 3ms 就算一包
结束」来分包，客户端虽然已经按 4ms 排队发，但网络抖动会把两包挤到一起到达，
那样芯片会把它们粘成一包然后越解析越乱。

### 键鼠延迟：三个非改不可的地方

本机实测键鼠往返（浏览器发出 → 桥 → 串口 → 芯片 → 原路回来）**4.8 ms**，其中串口
段 4.7 ms，网络和 TLS 只占 0.1 ms 上下。达到这个数要做三件事，少一件就会明显变慢：

**关 Nagle。** 键鼠包十几字节、应答七字节，Nagle 会把小包攒住等前一包被确认，
和对端的延迟确认一撞能压出几十毫秒。`axum-server` 备了 `NoDelayAcceptor`，但
默认不启用，得自己套上去。

**把系统定时器精度提到 1 ms。** Windows 默认是 **15.6 ms**，`recv_timeout(1ms)`
实际要睡满一个 tick 才醒，串口轮询循环于是只有 64 Hz——芯片的应答最多晚 15.6 ms
才被发现，而 `ch9329.js` 要收到上一包的回复才发下一包，整条链路被钉死在
64 包/秒。改之前实测往返 **15.6 ms 且方差极小**（正是 tick 的指纹），改之后
**4.8 ms、211 包/秒**。

顺带一提，客户端**不要**再加一层按帧合并的限流。`ch9329.js` 的 `writeMove` 本来
就只在队列里保留最新一个移动包，天然跟着串口速度走；外面再包一层
`requestAnimationFrame` 只会把更新率钉死在 60 Hz，还平白多等半帧。

**输入不要等芯片应答。** `ch9329.js` 原本是插在本机 USB 口上跑的，等每一包的应答
几乎不要钱。搬到网络上之后，这个「等」变成了拿**远端往返**去给一条 5 ms 的本地串口
做流控：实测客户端离宿主机 82 ms 时，发包率被钉死在 11 包/秒，浏览器每秒产生的
61 个移动事件有 50 个被合并掉了，光标肉眼可见地一跳一跳。所以移动和按键走
「只发不等」（`_ackSupported = false`），只有连接探测和显式查询（`getInfo` 之类）
才临时把等应答打开——那些地方确实需要读回内容，而且一秒最多几次。

延迟读数因此也要改。原来的算法假设一问一答，用「最近一次发出」配「下一次收到」；
不等应答之后这个配对就错了——回复要八十多毫秒才回来，那时候 `_sentAt` 早被后面的
包覆盖成几毫秒前，量出来是个毫无意义的小数字（看着像 6 ms，实际一点没变快）。现在
改成两个各自量得准的数：**网络**段由客户端在 `/ws/serial` 上显式 ping/pong，
**串口**段由服务端在串口线程里量 TX→RX 后捎在 pong 里。对远程客户端来说，网络那一
项就是延迟的全部来源，也是唯一改不了的一项。

### 控制页布局：一条左侧浮动工具栏，没有别的

照搬 chrome-kvm：`position: fixed; top: 50%` 垂直居中贴左边缘，默认收起
（`transform: translate(-100%, -50%)` 整条滑出屏幕，只留右边一截把手），38×38 的
内联 SVG 图标，hover 出右侧 tooltip。图标不用 emoji——各系统渲染差异太大，语义也常对不上。

按钮分三组：

1. **状态兼开关**：画面、键鼠、声音。图标本身按 `status-idle/ok/warn/error` 变色
   （灰/绿/黄/红），详情在 tooltip 里。点击各有动作：画面立刻重读服务端读数、键鼠
   「没连就连、连上了就刷新芯片状态」、声音开关。键鼠图标下面是 Num / Caps / Scroll
   三颗键盘指示灯（`1 A ⇩`），绿色为亮，点一下给被控端按一次对应的锁定键。
2. **观看**：连接信息（开关左上角那块叠加层，关掉时图标自己也暗下来，否则看不出
   当前是开还是关）、全屏（连带 Keyboard Lock）、显示方式、截图、录制。
3. **其他**：识别文字、快捷键（Ctrl+Alt+Del 在里面）、粘贴、松开所有键、ATX 电源
   （设置页选了继电器才出现）、切换被控机（存了两份以上配置才出现）、设置、刷新。

**控制页上除了这条工具栏和统计叠加层，什么都没有了。** 原来右上角那个面板整块删掉：

- 串口和鼠标模式两个下拉框是**和设置页重复的**——同一件事两处都能改，改哪个生效
  得靠记。现在控制页只读配置（`/api/config`），串口由「配置里指定的 > 报得出产品名的
  那个 > 第一个」定下来，写入只在设置页。
- 剩下的（连接按钮、串口状态、延迟读数、声音开关、声音状态）全部折进上面那三个状态
  图标，文字进 tooltip。统计叠加层的开关给了自己的按钮——开关这种东西藏在别的图标
  的点击里、只在 tooltip 提一句，等于没有。
- **动作结果做成底部提示条**（`#toast`，4 秒自净，报错的留 10 秒）。38px 的图标栏里
  塞不进一行文字，而 chrome-kvm 用的 `alert()` 会打断操作、还要多点一下才能继续。

三个状态图标共用 `StatusText.applyStatus(button, tooltip, state)`。它用 `classList`
增删而不是覆盖 `className`——按钮上还挂着别的类（录制按钮的 `.recording`），
整个覆盖会把它们一起抹掉。

`describeVideo` 换成了 `describeStream`：前者问的是 `track.readyState` / `track.muted`，
而这边画面走 WebSocket，根本没有 `MediaStreamTrack`，状态只能从「连接状态 + 服务端
读数 + 本机绘制计数」推。顺带能报一种原来看不出来的故障：帧收到了但一帧没画出来
（`received > 0 && drawn === 0`），那是解码全失败，光看 fps 是发现不了的。

### 录制要另开一块画布

显示用的画布已经 `transferControlToOffscreen()` 交给 Worker 了（1080p30 的 JPEG 解码
压在主线程上会连带把输入响应拖卡）。这带来一个后果：**主线程那个 `<canvas>` 元素
不再被绘制，对它 `captureStream()` 只会录到黑屏**。而 `OffscreenCanvas` 自己没有
`captureStream`，它只有 `convertToBlob` 和 `transferToImageBitmap`。

所以录制单独开一块不进 DOM 的画布：Worker 画完 OffscreenCanvas 之后，把**同一个**
`ImageBitmap` 转移给主线程。`drawImage` 是同步的，返回时像素已经在画布里，之后转移
走这个 bitmap 是安全的——正因为能这样，录制不用重复解码一次。不录的时候 Worker
连帧都不发，开销为零。

两个细节：

- 用 `captureStream(0)` 的**手动模式**，每收一帧调一次 `requestFrame()`。自动模式下
  帧的产生取决于画布有没有被合成器绘制，而这块画布根本不在 DOM 里，不能指望。
- 画布尺寸必须在 `captureStream()` **之前**定好：track 的分辨率取自调用那一刻的
  画布大小，之后再变会让 WebM 里的分辨率和实际帧不一致。

声音开着的话会一起录进去（`MediaStreamAudioDestinationNode` 常挂在播放图上，
多一个目标节点的开销等于零）。已知粗糙处：声音重连会重建 AudioContext，录制中途
碰上的话后半段没声。

### 粘贴是逐字模拟按键，不是真的粘贴

读剪贴板然后用 `ch9329.js` 的 `typeText` 一个字符一个字符敲进去。两个限制是方式
本身带来的，修不了：

- **非 US 键盘字符输不了**（中文之类），映射表返回 null 就跳过并计数。
- **慢**。一个字符是「按下 + 抬起」两包。这里故意不开 ACK：开了就要跨网络等两次
  应答，82ms 的链路上一个字符要三分之一秒。关掉之后走 ch9329.js 自己的 20ms 包
  间隔，一个字符 40ms，所以按钮上会先报个预计耗时。

### 快捷键面板

照搬 chrome-kvm 的那套（`web/shortcuts.js` 管解析和预设，`web/shortcut-panel.js` 管
界面，Android 端 `Shortcuts.kt` 是同一套规则）。不是在浏览器里模拟组合键，而是让芯片
直接对被控端发 HID 报告，所以 Ctrl+Alt+Del、Win+L、Alt+Tab 这些被本机系统吃掉的组合键
也能送到被控端。工具栏原来单独那个 Ctrl+Alt+Del 按钮因此去掉了，它在 Windows 那组里。

- **写法**：`+` 连接同时按的键，空格或逗号分隔多步（`Win+R Enter`），步间隔 150ms，
  好让被控端的弹窗画出来再接下一步。修饰键别名不分大小写，Mac 的 Cmd/Option 映射到
  Win/Alt。一步最多 6 个普通键（一份 HID 报告的上限），一个快捷键最多 16 步。
- **发法**（`Ch9329.tapCombo`）：有修饰键也有普通键时先单独发一包修饰键，再发修饰键 +
  普通键，最后全松开——有的系统要先看到 Ctrl/Win 按住才把随后的键当快捷键。有不认识
  的键就一包都不发，不发缺键的组合。
- **开机连按**：BIOS 只在自检那一两秒认热键。打开开关后点的键每 0.2 秒按一次，最长
  60 秒，点任何快捷键或关开关就停；连按期间本机键盘不转发，断线重连后自动停（不会
  接着往新连接上按）。
- **自定义**：最多 30 条，网页端存 `localStorage`（多标签页同步），Android 端存
  SharedPreferences。存储里的坏条目读出来时丢掉，不整个作废。
- 面板里的输入框打字不会发给被控端；粘贴进行中按快捷键会被拒绝，免得两边交错。

测试：`node --test "tests/web/*.test.js"`。

### 识别文字（OCR）

照搬 chrome-kvm：点工具栏「识别文字」，在画面上拖一个框，框里的字在本机识别出来，
放进可编辑的面板并自动复制。用来把蓝屏错误码、BIOS 信息、没法复制的报错拿回本机。
`web/ocr.js` 是纯逻辑（区域换算、预处理、结果整理），`web/ocr-panel.js` 管框选和调引擎。

- **引擎随站点提供，完全离线**：`web/vendor/tesseract/` 放了 Tesseract.js 7（SIMD 版和
  通用版各一份 wasm）和英文、简体、繁体三个语言包，共约 14 MB。第一次点才加载，闲置
  3 分钟释放。画面不会发到任何服务器。日文、韩文语言包没带——Android 宿主机会把整个
  `web/` 打进 APK，能省则省。
- **截图走 Worker**：显示画布已经交给 Worker，主线程读不到像素；也不能等下一帧，MJPEG
  画面静止时服务端一帧都不发。所以 Worker 收到 `snapshot` 就 `createImageBitmap(canvas)`
  复制一份当前画面回来（`transferToImageBitmap` 会把显示中的画布清空，不能用）。
- **框选期间什么都不发给被控端**：全屏遮罩挡住鼠标，键盘在 window 捕获阶段截住；Esc 或
  右键取消。框选那一刻就截图，不受引擎加载耗时影响。
- **预处理**：小区域放大 2～3 倍（Tesseract 认二三十像素高的字最准），转灰度，整体偏暗
  （BIOS 蓝底白字、终端）时反色。
- **中英混排认两遍**：先英文优先，结果里有汉字再中文优先重认。代价是同一块里既有中文
  又有十六进制码时数字容易认乱，这时只框错误码那一行。
- 结果去掉汉字间多余的空格、夹在汉字间的半角标点转全角。明文 http 的局域网地址写不了
  剪贴板，点「复制」会选中文字让你自己按 Ctrl+C。

### 浅色主题

照搬 chrome-kvm 的 `theme.js` / `theme.css`：设置页最上面「外观」选跟随系统、浅色或深色，
立即生效，存在本机浏览器（`rust-kvm-theme`），多标签页同步。两个页面的颜色全部走
`theme.css` 里的变量，深色下的半透明白叠加在浅色下换成同等分量的半透明黑，层次不变。
`theme.js` 在 `<head>` 里同步执行，赶在绘制前定下主题，不会先闪一下深色。画面四周的
留白在浅色下也保持深色——被控端多半是深色桌面，白边框着反而刺眼。

### 被控机配置

照搬 chrome-kvm 的 `profiles.js`：一台 KVM 接多台机器（或配了切换器）时，每台的采集设备、
分辨率、帧率、采音设备、串口、鼠标模式各存一份。设置页顶上「被控机配置」可以另存为
（同名覆盖，最多 20 份）、切换、删除（点两下确认）；当前用着某份配置时点「保存」会同步
进那份。存了两份以上时控制页工具栏出现「切换被控机」，点一下就切过去并把键鼠重连到
新串口，画面由服务端在设备或分辨率变了时自己重开。

- **只存跟着被控机走的字段**。编码、码率、窄带取决于现在走的是哪条链路，波特率记的是
  CH9329 芯片自己的状态，切换时都保持当前值。
- **配置存在浏览器里**（`rust-kvm-profiles`），不在服务端：服务端只有一份当前配置，切换
  就是把存的字段合并进去再整份写回 `/api/config`（服务端字段都是 `serde(default)`，
  只写一部分会把其余的重置）。换台电脑或浏览器要重新存。
- **继电器也跟着配置走**。切到一份没设过继电器的配置（包括这个功能上线前存的）时，电源
  按钮会消失，不会沿用上一台的继电器，免得按下去关掉的是另一台机器。

### ATX 电源

照搬 chrome-kvm：被控机死机、关机后键鼠就帮不上忙了，接一块 LCUS 系列 USB 串口继电器
到机箱电源键上，就能在控制页远程按电源键。和 chrome-kvm 不同的是继电器插在**宿主机**
（跑 rust-kvm 的这台）上，指令由服务端发。

**接线**：机箱电源键只是个轻触开关，按下时把主板前面板跳线上 `PWR_SW`（也标 `PWRBTN`、
`PW+ PW-`）两根针短接一下。用一母转二公的杜邦线把这两根针分出来，一路插回机箱电源键的线，
另一路接继电器的 `COM` 和 `NO`（常开）端子。不分正负，**不要接 `NC`**。两路以上的继电器
可以用同样的办法把另一路接到 `RESET` 两根针上。继电器要买**串口版**（板上是 CH340，插上
多一个 COM 口，指令是 `A0 01 01 A2` 这类），免驱 HID 版不行。详细图解见 chrome-kvm 的 README。

**设置**：设置页「ATX 电源」选继电器的 COM 口、电源键通道，接了复位键再选复位键通道，点
「保存」。工具栏「切换被控机」旁边会多出电源按钮。接被控机之前可以先空跑一次：点「按一下
电源键」应该能听到「咔哒」两声。

- **三种按法**：短按 500ms（开机，或让系统正常关机）；长按 6 秒（强制断电，ATX 规范是 4 秒，
  多留点余量）；复位 500ms。长按和复位会丢数据，要 4 秒内连点两下，确认只对最后点的那个
  按钮有效。长按时面板里有「松开」可以提前结束。
- **断开指令一定会发**：一次按压从开串口、吸合、等待到断开，全在服务端的一个独立线程里跑完，
  和发起它的请求无关。页面关了、网断了，到时间照样松开；吸合指令写失败也照样补发断开。
  chrome-kvm 长按时关掉页面会让继电器一直吸合，这里没有这个问题。
- **认口不认型号**：继电器和 CH9329 多半都是 CH340，厂商号产品号一样。服务端直接按 COM 口名
  打开，不存在 chrome-kvm 那种「分不清哪个是继电器」；同一个口不能既是键鼠又是继电器，保存时
  会拒绝。
- **只在按的那一下打开**，按完就关，平时不占串口。一次只按一下，上一下没完就点会被拒绝。
- 协议：`A0 通道 状态 校验`，状态 `01` 吸合、`00` 断开，校验是前三字节和的低 8 位
  （`src/atx.rs`）。接口是 `POST /api/atx/press {"kind":"short"|"long"|"reset"}`（按完才返回）
  和 `POST /api/atx/release`。
- Android 宿主机还没有这两个接口，那边的配置里也没有继电器，电源按钮不会出现。

### 本机 USB 口直连：虚拟光驱、U 盘和键鼠（ARM 板）

宿主机是带 USB 设备口的 ARM 板（RK3566 / RK3588 一类、树莓派 4/5 的 USB-C 口）时，用一根
USB 线把板子的设备口接到被控机，被控机会看到一个光驱、一个 U 盘和一套键鼠：

- **光驱**挂 `.iso`，可以从它装系统、在 BIOS 里从它启动；
- **U 盘**挂 `.img` 或 `.iso`，可以选只读；
- **键鼠**可以代替 CH9329：设置页「键鼠」的串口选「本机 USB 口直连」。CH9329 芯片那一节
  这时会隐藏，键盘指示灯照常工作。两者可以同时接，用哪个看串口选的是哪个。

被控机上一直能看到一个空光驱和一个「无介质」的可移动盘，跟插着读卡器一样；挂盘、换盘、
弹盘都不会让键盘掉线。挂载状态不跨服务重启保留。

**前提**：

- 内核开了 `CONFIG_USB_CONFIGFS`，`libcomposite` 能加载；
- `/sys/class/udc` 下有控制器。RK 板的 OTG 口在很多镜像里默认是主机模式，要在设备树里把
  那个 `usb@…` 节点的 `dr_mode` 改成 `"peripheral"` 或 `"otg"`，重启后才会出现；
- 用新版程序重新 `sudo rust-kvm install`。ARM 上的单元文件会多一行
  `ExecStartPre=-+… usb-gadget-setup <用户>`：每次启动前以 root 建 gadget、绑定控制器、把
  挂盘和 `/dev/hidg*` 交给服务用户；建不起来也不挡服务启动，原因显示在设置页「键鼠」一节。

**镜像**放在资源目录下的 `images/`（服务第一次在可用的板子上启动时建），控制页「虚拟介质」
面板里可以上传和删除，也可以直接 scp 进去。想放到别的盘上，把 `images` 做成软链接。

不是按页面上缩放后的尺寸，小字才看得清。下载 `screenshot-年月日-时分秒.png`，同时复制到剪贴板；
剪贴板只在 https 或 localhost 下可用，用不了就只下载。

**显示方式**：适应窗口（默认）、拉伸铺满、原始像素 1:1、放大 1.5× / 2× / 3×，存在本机浏览器里。
放大后画面比窗口大的方向跟着鼠标走：指针在窗口左边缘时看到画面最左边，右边缘时看到最右边，
指针下面正好是它在画面里对应的那一点，本机光标和被控端光标始终重合。和 chrome-kvm 不同，
这边显示的是画布不是 `<video>`，`object-fit` 在画布上靠不住，所以 `view-modes.js` 对每种方式
都直接算出画布的框（拉伸也是），框正好等于画面内容，`ch9329.js` 按画布布局框换算绝对坐标的
那套就不用改。画面尺寸由 Worker 在改画布尺寸时报给主线程（`KvmVideo.size()`）——画布移交之后
主线程读它的 `width` 不会跟着变。

**键盘指示灯**：芯片只在被问到时才报灯的状态，所以每 2 秒问一次——被控端开机自检、登录界面
会自己改 Num Lock，光凭本机按过什么键推算不准。代价在于这边的键鼠平时是只发不等应答的，
问的那一下要临时开回应答等待，期间的键鼠包都得等确认；所以最近 0.5 秒内有操作就跳过这一轮，
粘贴、开机连按期间也不问。按锁定键、点小灯后 150ms 补查一次。连着两次没应答才算芯片无应答。
被控端没枚举出 USB 键盘时灯是藏起来的。

### 装成服务：不只是开机自启

```
rust-kvm install     注册成开机自启的服务（要管理员权限）
rust-kvm start       启动
rust-kvm stop        停止
rust-kvm status      看状态和日志位置
rust-kvm uninstall   卸载
rust-kvm             不带参数就在当前窗口跑，Ctrl+C 停
```

真正的理由是**音频**：服务以 LocalSystem 跑在 session 0，那是唯一能枚举到物理音频
端点的地方。远程桌面会话里 cpal 报零个输入设备，装成服务之后立刻变成五个，
其中就有采集卡的 `Digital Audio Interface (USB Digital Audio)`。所以
`account_name: None`（LocalSystem）不是随手选的默认值，是必须的。

两个容易踩的地方：

- **不能依赖当前工作目录**。服务是被 SCM 拉起来的，工作目录是 `C:\Windows\System32`，
  相对路径全部作废，也不该往那儿写证书和日志。`asset_root()` 改成从 exe 位置**往上找**
  第一个含 `web/` 的目录——往上而不是就看旁边，因为 `cargo run` 时 exe 在
  `target/debug/` 里，资源在两层之上。
- **服务里没有 stdout**，日志只能进文件（`rust-kvm.log`），而且要在 `service_main`
  的最开头就配好。晚一步的话，之后出的任何错都会安静消失，从外面只能看到
  「服务启动后又停止了」这种毫无线索的提示。

停止走优雅关闭而不是直接退：主要是让串口线程把「全释放」包发出去——服务停的时候，
被控机上不该留着按下不放的键。同样的理由，控制台模式下 Ctrl+C 也接了这条路径。

### start.ps1 / stop.ps1：上面那些命令包一层

```
.\start.ps1              启动服务（没装会先注册），等到真能访问才返回
.\start.ps1 -Dev         前台跑，日志打在当前窗口
.\start.ps1 -Build       先停掉实例再 cargo build --release，然后启动
.\stop.ps1               服务和前台实例一起停，停到 exe 可写为止
```

`rust-kvm start/stop` 已经够用了，脚本补的是它没法管的那些：

- **只在真要动服务时才提权**。前台调试实例不需要管理员，日常调试不该弹 UAC。
- **「停了」要停到 exe 可写**。进程列表空了不等于文件句柄放开了，紧接着
  `cargo build` 照样会失败，报错只说「拒绝访问」，不说是谁占着。所以停完要实测
  能不能独占打开 exe。
- **不信停止命令的回执，只信复查**。SCM 的停止是异步的，服务收尾要好几秒，
  `Stop-Service` 的耐心比这短，会抛「停止失败」——其实过一会就停了。脚本把这类
  抱怨当噪音，最后统一复查服务状态、进程、文件句柄、端口四样。
- **`CARGO_TARGET_DIR` 钉死**。不钉的话 build 可能落到别处的缓存目录，编译显示
  成功，跑起来的还是 `target\release` 里那个旧的——这个坑很难看出来。
- **就绪判据探明文的 8080 而不是 8443**。PowerShell 5.1 那套 .NET Framework 的 TLS
  栈连不上自签名证书，报「未能创建 SSL/TLS 安全通道」，跳过证书校验也没用，拿它
  当判据会把好好的服务误判成起不来。

脚本本身有两个编码坑，都踩过：`.ps1` 必须存成 **UTF-8 with BOM**，否则
PowerShell 5.1 按 GBK 读，中文注释和字符串全是乱码；exe 往 stdout 写 UTF-8，要
**临时**把 `[Console]::OutputEncoding` 切成 UTF-8 再切回来——全局改掉的话，脚本
自己的输出被重定向时又全乱了。

### Linux 宿主机

```bash
cargo build --release
sudo target/release/rust-kvm install     # 拷到 /usr/local/bin，写 systemd 单元并 enable
sudo rust-kvm start                      # 等到 8080 真能连上才返回
journalctl -u rust-kvm -f                # 日志
```

`install` 要在项目目录里跑：资源目录（`web/`、`certs/`、`config.json`）就是这里，
单元文件的 `WorkingDirectory` 指过来。程序本身拷到 `/usr/local/bin/rust-kvm`，服务
跑的是那份拷贝——`target/` 会被 `cargo clean` 清掉，`CARGO_TARGET_DIR` 还可能在
`/tmp` 下，直接指过去的话重启后服务就起不来。重新编译后再跑一次 `install` 换程序，
服务在跑的话 `stop` 再 `start` 才生效。

和 Windows 不同，装成服务**只是**为了开机自启——Linux 没有会话隔离，前台跑看到的
设备和服务里一样。要操心的是权限：桌面登录时 logind 给当前用户挂了设备 ACL，所以
前台跑一切正常；服务不在登录会话里，那条 ACL 不作数。单元文件因此以执行 `install`
的那个用户（`SUDO_USER`）身份跑，附加 `video` / `audio` / `dialout` 组（不存在的组
跳过，写进去服务会直接起不来），再给 `LimitRTPRIO`。不用 root 跑是因为 `certs/` 和
`config.json` 归这个用户，root 写过之后再前台跑就改不动了。`systemctl stop` 发的
SIGTERM 和 Ctrl+C 走同一条优雅关闭路径，「全释放」包照发。

H.264 走 openh264 软件编码（源码随 crate 编进来，不依赖系统库）。动态画面码率卡在
设定的上限，静止画面 0.003 Mbps。`probe-h264 -- --bench frame.jpg 60` 分段量单帧耗时，
i5-12450H 上 1080p：JPEG→NV12 7–10 ms，编码 8–10 ms（带 nasm 汇编）。两段串着是
18 ms，超了 60fps 的 16.7 ms，所以解码和编码拆成两个线程流水线跑，吞吐只看慢的那段，
60fps 有余量。两段之间是两块 NV12 缓冲加一个容量 0 的交接，最多压一帧，不加延迟。

解码线程按配置的帧率抽帧，多出来的帧连解码都不做：MS2109 接 60Hz 的源时会无视请求
照吐 60fps，配置 30 时不抽的话白白多解一倍。落后时只取广播里最新那帧，不去追旧的。
openh264 没有 MF 那种「恒定质量 + 上限」，用的是码率模式加跳帧：
画面不动时宏块全是 skip，动得太猛时宁可丢帧也不超预算。只出 Constrained Baseline
（`avc1.42C028`），浏览器都认。

移植时踩到的几个坑，都是 Windows 上不存在的：

- **nokhwa 把整块 mmap 缓冲区当一帧交出来。** V4L2 的缓冲区按 YUYV 最坏情况分配
  （1080p 是 4 MB），JPEG 只有八十来 KB，nokhwa 却丢掉了内核报的 `bytesused`。
  不处理的话每帧发 4 MB，实测 816 Mbps。`video.rs` 的 `jpeg_len` 从 SOI 按段走到
  EOI 再裁——不能从尾部往前找 `FFD9`，缓冲区是复用的，上一帧更长时它的旧 EOI
  还留在后面。
- **UVC 摄像头有两个 `/dev/video*`**，后一个只吐元数据，名字一模一样，nokhwa 还把
  它排在前面。「没指定设备就用第一个」正好打开它，报一句毫无线索的
  `Could not get device property CameraFormat`。`camera.rs` 按 `VIDIOC_QUERYCAP` 筛掉。
- **ALSA 把同一张卡列成好几项**（`hw:`、`plughw:`、`dsnoop:`、`front:`…），名字
  一字不差，采样率却不同（`hw:` 是设备原生格式，`plughw:` 会帮你转换）。
  `/api/devices` 带上 cpal 的设备 ID，设置页只在同名时用 ID 当值。
- **`/dev/ttyS0`–`ttyS31` 不管有没有硬件都在**，串口下拉框三十多项。sysfs 里
  `type` 为 0 的筛掉。
- **cpal 的 `realtime` 在 Linux 上是个静默的空操作**（要另开 `realtime-dbus` 才去找
  rtkit，无头机器上多半也没有）。采音线程改由 `promote_audio_thread` 自己提到
  `SCHED_FIFO`，只对直通硬件的 PCM 提——走 PipeWire 的那些实时活儿在音频服务器里，
  `null` 设备的 poll 永远立刻返回，提上去会吃满一个核。前台跑没有权限，日志里会有
  一条警告，不影响采音。

MS2109 上实测：

- **音频格式内核已经改正。** ALSA 报的就是 48000 Hz 双声道 S16_LE，
  `hdmi_stereo_quirk` 只在设备自报 96k 单声道时才触发，所以不会修两遍。字节对齐
  （Windows 上那个差一个采样的错位）还没测到：当时 HDMI 源没送声音，录到的全是 0。
- **刚开流会吐几帧不是 JPEG 的缓冲区**（开头不是 `FFD8`），多见于关了马上重开。
  以前 MJPEG 那路会把整块 4 MB 发出去，H.264 那路解码失败就整条回落到 MJPEG。现在
  采集循环直接丢掉没有 SOI 的缓冲区，编码线程也只在连续 30 帧解不开时才回落。
- 视频 1080p30 MJPEG，裁剪后约 38–64 Mbps（看画面），裁之前是 983 Mbps。
- **1080p60 是假的。** 能力表里有，也真按 60fps 出帧，但每隔一帧是个只有
  `FFD8 FFD9`（SOI+EOI）的 4 字节空 JPEG，真画面还是 30 帧；而且真帧和空帧是挨着到
  的。编码线程落后时只取最新那帧，于是次次挑中空帧、连错 30 帧整路回落 MJPEG。现在
  采集循环把空帧丢掉，选 1080p60 等于 1080p30。**要真 60 帧得选 720p**（1280x720，
  实测每帧都是完整画面，约 108 KB）。

### 设置页：设备列表只能由服务端给

远程浏览器没有宿主机的 `getUserMedia` / Web Serial 权限，所以不能再走 chrome-kvm
那套「浏览器弹窗授权选设备」。`/api/devices` 由服务端枚举后交给页面。

**每一类设备都带自己的 `error`**，而不是整体失败或者返回空列表了事。空列表的原因
往往才是用户真正需要知道的——尤其音频：远程桌面会话里物理端点根本不被枚举，光看到
一个空下拉框没人猜得出来是为什么，所以那条解释会直接红底显示在下拉框上方。

分辨率下拉框列的是采集卡 MJPEG 能力表里的档位（`/api/video/capabilities`），
MS2109 上是 1920×1080 到 640×480 共 11 档。查不到能力表时退回几档常见分辨率。
配置里存的分辨率不在表里（手改的、或从别的卡的配置切过来），照样留着，并标出
实际会退回哪一档，比如「1600×900 — 不支持，实际为 1600×1200」——服务端按「最接近」
协商。Linux 上这次只枚举格式，不开流，正在看画面时也能问。帧率不能信能力表——MS2109 的 1080p 也写着 60，真画面只有 30。
高于 30 的选项按实测标：没人看就开流数 1.5 秒非空帧（`/api/video/measure`）；
正在采集的那一档直接用画面状态里的帧率，不把控制页掐掉。结果按设备记在浏览器里，
帧率后面的「重新检测」清掉重来。页面下方那行「实际 … fps」仍是当前这路的真相，
也是判断远程链路带宽够不够的依据。

**配置里存的设备名可能不在当前枚举结果里**（设备拔了，或者配置是手写的关键词而非
完整名字）。这种情况绝不能静悄悄地把选择重置成第一个设备——那等于用户一进设置页、
什么都没动、一点保存就把配置改掉了。所以会额外插一条「(当前配置，未检测到)」并选中它。

保存后热切换，但**只在相关配置真的变了时才动采集**：设置页会把整份配置推过来，
而一次只改了串口的保存不该把画面和声音各掐断一下。串口则完全不热切换——口是浏览器
通过 `/ws/serial` 的 `open` 打开的，配置只是给页面一个默认值。

### 写芯片配置要临时借串口

波特率、工作模式、恢复出厂这几项是写进 CH9329 芯片本身的，得由浏览器编好帧发下去
（和键鼠走同一条路）。设置页为此临时连一次 `/ws/serial`，**用完立刻还**——
不还的话控制页就再也连不上了。所有写操作共用一个 `withChip` 外壳来保证这一点。

串口同一时刻只能有一个控制端，所以别处连着时设置页借不到。借不到时会 `confirm`
一句要不要接管（见「控制权互斥」）——先礼后兵而不是直接抢：抢走的可能是别人正在用
的控制权，而这几项本来就是开机配一次的事，值得多问一句。

键鼠改成默认连接之后，「借不到」从边缘情况变成了常态：控制页一开着就占着串口。
不过从工具栏点「设置」是整页跳转，控制页卸载时串口就放了，所以同一台机器上这条路
一直是通的；接管是给**另一台设备**开着控制页时用的。

报错文案曾经**完全没说到点上**：`ch9329.js` 是从本地版原样搬来的，
它那句「请关掉其它开着本站的标签页」是针对 Web Serial 写的，在这儿根本不适用——
口是服务端开的，抢它的只可能是另一个 `/ws/serial` 控制端。

更麻烦的是真正的原因**会被盖掉**：服务端推的那条 `error` 常常被当成某条命令的失败
应答消化掉，调用方最后拿到的是随后连接断开产生的「串口桥已断开」——更晚、更没信息量。
所以 `SerialWsPort` 额外记一个 `lastServiceError`，写芯片失败时优先用它。旁边还记一个
`lastServiceErrorCode`，「被占用」就靠它认——不去匹配文案，文案是给人看的，随时会改。

工作模式**不存进 `config.json`**：芯片才是它唯一的真相，本地存一份过期的副本比不存
更糟。改成点「读取芯片配置」现问。读回来时还会比对「存着的波特率」和「刚才实际问通的
波特率」——两者不一致就说明上次写入还等着断电重插，那是最容易让人困惑的状态。

配置存成 `config.json` 而不是计划里写的 TOML：`serde_json` 本来就在依赖里，而主要
编辑入口是设置页，TOML 能写注释这个优势用不上。文件损坏时退回默认值并继续跑——
起不来的话连设置页都打不开，也就没法把它改回去。

### 音频：裸 PCM 加一个会自己长高的抖动缓冲

服务端 `cpal` 采到什么格式就按什么格式发，不重采样也不压缩：一条 Text 报
`{sampleRate, channels, format}`，随后每条 Binary 是一块 10ms 的 Int16 LE。48kHz
立体声是 1536 kbps，挨着 20 Mbps 的视频不值一提，换 Opus 的复杂度暂时不划算。

客户端拿这个采样率**直接建 AudioContext**，于是 worklet 收到的样本率恰好等于上下文
采样率，一次重采样都不用做；真和声卡不符时由浏览器在输出端处理，那比手写的强。

麻烦都在时钟上：采集时钟在采集卡上，播放时钟在本机声卡上，两者永远差一点，长跑
必然漂移。所以 `audio-worklet.js` 里有一个环形缓冲加三条规矩：

- **攒够目标水位才起播**，否则一上来就断断续续
- **起播那一刻把多余的水位裁掉**。浏览器启动音频设备要一两百毫秒，这期间
  `process()` 一次都不会被调用而网络还在灌——不裁的话这段积压就变成永久延迟。
  实测不裁是稳在 270ms，裁了是 130–150ms（目标 100ms，余量来自 TCP 的成批到达）
- **欠载时把目标水位抬高一档**（40ms，上限 200ms）。固定水位在远程链路上走不通：
  抖动一旦超过水位就欠载，重新攒又回到同一个水位，于是一直咔咔响。让它自己往上爬，
  差链路上用一点延迟换不断音

缓冲涨过 400ms 则裁回目标，用一次轻微的咔哒换「延迟不会无限累积」。面板上
`缓冲 / 目标` 两个数都显示：目标明显高于 100ms 就说明这条链路抖得厉害。

### 键鼠和声音都默认连接

打开页面就连，不用点。原来两个都要手点一下，但那一下没有任何信息量——串口和鼠标
模式都在配置里，点与不点的结果完全一样。连不上也没关系：图标变红写明原因，点一下重试。

键鼠这边有个副作用要知道：控制页一开着就占着串口，设置页那节「读写芯片」要借串口
会借不到。不过从工具栏点「设置」是整页跳转，控制页卸载时串口就放了，那条路还是通的。

声音这边有个绕不过去的浏览器限制：**自动播放策略会把没有用户手势的 AudioContext
挂起。** 所以「默认开」实际是「默认连上并等第一次交互」。两个坑：

- **不能 `await ctx.resume()`。** 被策略拦住时 Chrome 让这个 promise 一直悬着（Safari
  和 Firefox 则是 reject），`await` 会让 `buildPlayer` 永远不返回，页面显示在播、实际
  一点声音没有。原来这里就是 `await`，能跑是因为那时必定有刚点过开关的那次手势。
- **挂起期间不能喂数据。** worklet 的 `process` 不跑，喂进去的 PCM 只会在它的消息
  队列里堆着，1536 kbps 堆五分钟就是五十多兆。

做法是挂起与否统一由 `ctx.onstatechange` 驱动（而不是只在建好时判一次，上下文中途
也可能被系统休眠或浏览器省电策略挂起），挂起时 `feeding = false` 并守住下一次
`pointerdown`/`keydown`。用户迟早要点一下画面去操作被控机，那一下就够了。这期间图标
是黄的，写着「等待页面交互后出声」——这个状态一定要说出来，否则就是「图标绿着、
读数在涨、人听不到声」，最容易让人以为是采集卡坏了。

### 音频格式是假的：自报 96k 单声道，实为 48k 立体声

MS2109 的 HDMI 音频口只提供一种配置：96000 Hz 单声道（U8/I16/I24/I32/F32/F64 全是
这一档），实测到达 95850 帧/秒，和自报的一致。但 HDMI 音频基本都是 48kHz 立体声，
而 `96000×1` 和 `48000×2` 的数据率一模一样——可疑。

**判据是奇偶不对称。** 对一路单声道时间序列来说，相邻差 `|x[i+1]-x[i]|` 的统计量不该
和下标奇偶有关。拿真实信号实测（23 万个样本对）：

| 配对 | 完全相等 | 平均差 |
|---|---|---|
| 偶-奇 | 0.2% | 262.8 |
| 奇-偶 | 21.8% | 74.2 |

差 3.5 倍。周期为 2 的结构只可能来自双声道交织；更相似的那一对落在奇数位，说明帧边界
从下标 1 开始，也就是**开头多了一个样本**。按这个解释拆开，两路各自的平滑度是
206.5 / 206.4、峰值 15569 / 15564——同一段音乐的左右声道。

这正是 Linux 内核给 `0x534d:0x2109` 设 `stream_offset_adj = 2` 要修的：2 字节正好一个
16 位样本。改完之后再测，同帧 L/R 的平均差从 74 降到 **20.0**，跨帧则升到 272——
对齐方向翻转，符合预期。

好在**一个字节都不用动**：交织的立体声本来就是我们的线上格式。要改的只有报出去的
格式（96000/1 → 48000/2）和丢掉整条流的第一个样本。后者要跨回调维持奇偶，
cpal 每次给的样本数不定，落单的那个必须留到下一块开头，否则左右声道会来回互换。

万一判错了，症状是左右对调加一个样本的错位，几乎听不出来——而不是变速。会变速的那个
假设（真·96k 单声道）已经被上面的奇偶不对称排除了。

### cpal 的实时优先级默认是关的（踩过，会爆音）

日志里反复出现 `音频流错误: A buffer underrun or overrun occurred.`，一两分钟一次，
听感上是偶发爆音。

这条错误在 Windows 上**只有一个来源**——cpal 的 WASAPI 后端拿到了
`AUDCLNT_BUFFERFLAGS_DATA_DISCONTINUITY`。它的含义不是「可能有问题」而是
**样本真的丢了**：设备缓冲满了，旧数据在我们读走之前被丢弃。

根因是 cpal 的 `default = []`，**`realtime` feature 默认不开**。不开的话采音线程就是
普通优先级，而这台机器同时在从 USB 抓 1080p30 MJPEG（约 30 Mbps）、把它推出去、
可能还有浏览器在解码它、外加 RDP 在编码音视频。普通优先级的线程被抢占，错过 10ms
的截止时间，WASAPI 就丢样本。开了之后 cpal 会调 `AvSetMmThreadCharacteristics`，
失败再退回 `THREAD_PRIORITY_TIME_CRITICAL`：

```toml
cpal = { version = "0.18.2", features = ["realtime"] }
```

生效的凭据是日志里这一行（MMCSS 提升成功，没退回 `TIME_CRITICAL` 那条备用路径）：

```
INFO audio_thread_priority::rt_win: task 571 bumped to real time priority.
```

实测：改之前 4.8 分钟里 6 次（聚类成 3 次独立打嗝），改之后 7 分钟里 2 次（同一次，
相隔 50ms）——约 0.63 次/分降到 0.14 次/分，听感上爆音已经没有了。**注意服务要跑
release**：`publish` 里是逐样本循环加 f32→i16 转换，debug 不优化本身就在添柴。

残留说明瓶颈不止优先级。真要清零，下一步是把编码移出实时线程（回调里只往预分配
的槽 memcpy，转换/broadcast/统计都搬走），或者给 WASAPI 要个比默认 10ms 更大的缓冲。

顺带一个隐患：丢样本会**永久翻转左右声道**。上面那个交织 quirk 靠「丢掉开头一个
样本」对齐帧边界，中途再丢奇数个样本，从那一刻起 L/R 就一直是反的。cpal 不透出
丢了多少，没法补偿，只能不让它发生。

还有两个相关的上报 bug，都是「把瞬时打嗝当成了故障」，而且都拖了很久才发现：

**第一个**：`record_error` 原本被两处共用——采集循环退出时用，cpal 的错误回调也用，
而后者会无条件把 `capturing` 清成 false、`kbps` 清零。于是偶尔一次瞬时 underrun
之后，页面就永久显示「未采音 0 kbps」，而人明明还听得到声音。拆成了
`record_error`（真停了）和 `record_stream_error`（瞬时打嗝，只记消息）。

**第二个**：上面那一刀没切干净——两者仍然写同一个 `error` 字段，而
`mark_capturing(false)` 不清它。于是一条 underrun 消息会一直留到**下一次采音真正
启动**，而 `await_format` 正是用这个字段判断「采音能不能起来」的。时序是这样的：

1. 上一轮听音留下一条 `音频流错误: A buffer underrun or overrun occurred.`；
2. 没人听了，采音停，`format` 清空，但那条消息还在；
3. 下一个客户端连上来，采音线程还在启动、格式还没发；
4. `await_format` 第一次循环：格式是 None，错误非空 → 立刻回 `{op:"error"}`；
5. 浏览器收到就拆掉播放器、8 秒后才重试，图标变红写着「音频流错误」。

**声音是好的，一按开关就红。** 现在字段分成两个：`error` 只放致命错误（采音起不来
或已停），`stream_error` 放 cpal 的瞬时流错误；`await_format` 只看前者，
`/api/audio/stats` 两个都报（致命的优先）；新一轮采音启动时两个一起清。

教训是：**一个字段同时被「给人看」和「给代码做判断」两种用途读时，它必须只表达
一种含义。** 第一刀只拆了写入方，没拆字段，所以问题换了个地方又冒出来。

### 音频设备要看会话（踩过）

**远程桌面会话里枚举不到任何物理音频设备。** Windows 会把物理音频端点换成「远程
音频」，`cpal` 于是报「一个输入设备都没有」，而设备管理器里那张卡明明是好的。
视频没这个问题——摄像头不按会话隔离，所以这个坑只在音频这条路上等着。

判断方法：`query session` 看当前会话是不是 `rdp-tcp#*`，
`Get-PnpDevice -Class AudioEndpoint` 看端点列表里有没有物理设备。

所以服务得跑在能看见物理设备的会话里（控制台会话，或者注册成 Windows 服务）。
`pick_device` 找不到设备时会把这段原因直接回给页面，而不是留一句「没有设备」
让人去猜。

### 测试音源

```bash
RUST_KVM_AUDIO_TEST=1 cargo run
```

设了这个环境变量就用 440Hz 正弦代替真设备。存在的理由是把「设备能不能打开」和
「管线对不对」分开验证——上面那个会话问题会让真设备直接开不起来，没有这个开关的话，
客户端那一整套环形缓冲、抖动缓冲、欠载处理就得等到部署问题解决之后才第一次运行，
真出问题时也分不清是设备的事还是代码的事。

### 断线一定要松键

被控机上卡住一个 Ctrl 是远程最修不了的故障。所以有两道保险：客户端在 `blur` /
`visibilitychange` 时发 `forceReleaseAllInput`，服务端则在 WebSocket 断开时硬编
两个「全释放」包（键盘 8 字节全零、相对鼠标五字节全零）直接写出去。后者是为了兜住
浏览器崩了、网线拔了这种没人来得及发的情况，也是服务端唯一需要的一点协议知识。

### 控制权互斥，以及为什么必须能抢

串口是独占设备，同一时刻只允许一个控制端。纯观看的客户端不连 `/ws/serial`，
所以被挡住的只会是第二个想控制的人。

后来者不会被秒拒，而是先等 2 秒：上一个控制端断开后，它的任务还要下发全释放包、
等串口线程归还句柄，前后几十到几百毫秒。刷新页面正好落在这个窗口里，秒拒会让人
以为「明明没人用却说被占了」。

等不到就**可以抢**：`/ws/serial?takeover=1`（`=true`、光写 `?takeover` 也认）会先请
现任退位，再接手。现任的 select 里有一个分支在等这个退位信号，收到就照常走收尾
流程——下发全释放包、关串口、还座位，所以被抢走不会在被控机上留下按住的键。接管
方最多等 5 秒。实测换手 32 毫秒。

为什么非要有这条路：**信号量能等不能赶**。原来唯一的退出路径是持有者自己放手，
而持有者可能是另一台设备上、用户根本碰不到的标签页。这个真踩到了——开发机上一个
自动连接的标签页把 COM3 占了一小时，另一头反复重试十几次，每次只收到「请先关掉
那个标签页」，而那个标签页他压根碰不到。「先到先得 + 提示去关掉它」在只有一个人、
一台设备时看着没问题，一旦跨设备就是死路。

两头都不自动抢：

- **自动连接不带接管**。页面一打开就夺走别人的控制权是没人想要的行为，而且两个
  开着的标签页会互相抢到没完。
- **被抢的一方不自动重连**，只把图标变黄、写明「点击接管控制权」。同理：自动抢
  回来就是无限乒乓。

所以抢夺必须是人点的。被拒和被抢在页面上是同一个状态（黄色 + 可点接管），因为
这两种情形要做的事一模一样。这个状态靠服务端错误里的 `code: "busy"` 认，而不是
去匹配错误文案——文案是给人看的，随时会改。

## 已知的坑

- **静态文件必须带 `Cache-Control`**。`ServeDir` 默认什么缓存头都不发，浏览器就
  按启发式规则自己决定能存多久，结果是改完 js 刷新页面**还是旧的**，而且毫无迹象
  ——只会看到刚修好的 bug 又出现。真踩到了：改完 `serial-ws.js` 后页面跑的仍是旧版，
  排查了半天才发现问题不在代码里。现在所有响应统一加 `no-cache`（不是「不缓存」，
  是「每次都回来问一句」，配合 ETag 通常就是个 304）。
- **nokhwa 报的帧率不可信**：`camera_format().frame_rate()` 在 MS2109 上返回
  1fps，而实测是 29.5fps。所以帧率一律自己按帧间隔算，别读这个字段。
- **远程桌面会话里枚举不到物理音频设备**，物理端点会被换成「远程音频」。服务
  必须跑在控制台会话或 Windows 服务里。详见上面「音频设备要看会话」。
- **这张卡的音频自报「96000 Hz 单声道」，实际是 48000 Hz 立体声**（已证实，见下面
  「音频格式是假的」）。代码里按这个解释处理，`audio.rs::hdmi_stereo_quirk`。
- **本机这颗 CH9329 跑在 115200 而不是 9600**。不用手填：`Ch9329.BAUD_RATES`
  会依次试 9600 和 115200，取第一个能应答 `GET_INFO` 的，所以连接会比预期多花
  一两秒。改过芯片波特率后要断电重插才生效，这一步服务端代替不了。
- **排查串口用 `RUST_KVM_LOG=debug` 起服务**，日志里会打出每一包的收发字节
  （`TX` / `RX`），对着 CH9329 协议文档核对最直接。
- **`serialport` 在 Windows 上开的是同步句柄**（`CreateFileW` 不带
  `FILE_FLAG_OVERLAPPED`），所以一个线程没法同时等通道和串口，只能轮询；COM 口
  又是独占设备，开不出第二个文件对象来绕开。要彻底摆脱轮询得自己写重叠 I/O。
  在轮询这个前提下，把定时器精度提到 1 ms 就是正解。
